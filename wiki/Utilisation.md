# Utilisation détaillée

[Accueil](Home.md)

## Utilisation

Pour commencer avec un exemple concret, suivez [le parcours correspondant à votre projet](Home.md). Le bouton [Peupler](Peupler.md) organise vos sources ; [la file des modifications](Modifications.md) signale vos retouches à Codex.

Activez **Orelius** dans les modules complémentaires d’Obsidian. Ouvrez ensuite **Orelius : Ouvrir le chat** depuis la palette de commandes, ou cliquez sur l’icône de discussion du ruban.

Dans **Réglages → Orelius**, l’installation de Codex est détectée automatiquement. Si elle n’est pas trouvée, utilisez **Rechercher Codex** ; un champ de chemin manuel apparaît si cette recherche échoue. **Tester Codex**, juste sous l’installation, vérifie l’exécutable et son authentification indépendamment du dossier de travail. Codex utilise son authentification existante ; si nécessaire, lancez `codex login` dans le terminal.

Le bouton **Parcourir…** ouvre le sélecteur Obsidian pour choisir un dossier du coffre, y compris sa racine. Les modifications sont enregistrées automatiquement.

Dans **Organisation du projet**, les noms des dossiers sont personnalisables : **Archives**, **Manuscript**, **Model** et **Bible** par défaut. Les dossiers du manuscrit et des textes modèles contiennent chacun **Chapitres**, **Personnages**, **Plan** et **Resume**. **Model** accueille une version antérieure du texte ou un texte à adapter ; Codex consulte ces sources et écrit le résultat dans **Manuscript**, en préservant les sources sauf demande explicite de modification. Le dossier d’archives reprend la structure sous `Archives/Manuscript/`, `Archives/Model/` et `Archives/Bible/`, avec les noms configurés. Les dossiers manquants sont créés au choix du dossier de travail, à la sortie d’un champ de nom ou à l’ouverture du chat. Un changement de nom utilise de nouveaux chemins ; les dossiers et fichiers existants, y compris les anciennes archives dans `_Archives`, sont conservés sur place. Ces noms s’appliquent aux différents dossiers de travail.

Dans l’explorateur de fichiers, cliquer sur le dossier de travail, un sous-dossier ou une note qu’il contient ouvre automatiquement le chat. La navigation entre notes par onglets ou liens suit le même comportement. Sortir des dossiers connus masque le panneau et restaure l’état ouvert ou replié de la barre latérale droite avant l’ouverture du chat ; revenir dans le dossier le réaffiche avec ses messages à jour. Un dossier dont la conversation est déjà enregistrée retrouve sa propre session. Si plusieurs dossiers associés sont imbriqués, le plus précis est utilisé. Pendant une tâche, naviguer dans un autre dossier masque le chat et laisse Codex continuer dans son dossier initial ; une autre session ne peut être activée qu’une fois la tâche terminée ou arrêtée.

Écrivez un message, puis utilisez **Envoyer** ou **⌘/Ctrl + Entrée**. Pendant le travail, la saisie reste disponible : **Envoyer à la tâche** transmet une consigne supplémentaire au tour courant avec `turn/steer`, sans l’interrompre ni créer une autre conversation. Un indicateur animé près du champ affiche l’activité ; une consigne acceptée est confirmée dans le chat. Pendant la connexion, l’interruption ou l’enregistrement du suivi, vous pouvez préparer le message suivant. **Arrêter** interrompt la tâche ; pendant une connexion, il ferme cette connexion. **Nouvelle conversation** détache la conversation courante sans supprimer son historique Codex. Fermer ou masquer le panneau conserve la connexion et la tâche en arrière-plan. Désactiver le plugin arrête les processus lancés par Orelius.

Le panneau affiche le modèle actif dans un sélecteur alimenté par le catalogue de Codex. Le changer reprend la même session avec le modèle choisi et conserve l’historique ; la sélection est indisponible pendant une tâche. À l’ouverture du panneau, la connexion charge le catalogue sans créer de conversation vide. **Contexte disponible** indique le pourcentage de la fenêtre de contexte restant selon la dernière mesure Codex, à partir du dernier usage et de la capacité annoncée par le serveur. `—` signifie qu’aucune mesure exploitable n’est disponible, notamment avant la première réponse ou après un changement de modèle. La valeur se met à jour lors des événements d’usage, y compris après compaction.

Si le modèle est temporairement saturé côté OpenAI, un encadré persistant précise que votre quota n’est pas épuisé et propose **Relancer**. Cet encadré reste visible avec les activités masquées et retrouve le dernier échec à la réouverture de la conversation. La relance conserve la demande, la conversation et les protections de révision ; l’archivage reste obligatoire. Si le chapitre a changé depuis l’échec, utilisez **Réviser** pour préparer une nouvelle demande. Aucune relance n’est automatique.

Pour reprendre un chapitre, ouvrez-le puis cliquez sur **Réviser**. Vos annotations et corrections constituent des exemples de votre intention, applicable à tout le chapitre. Le message éventuel précise la demande. Orelius autorise les raccords nécessaires dans le chapitre entier ; Codex doit préserver les passages qui répondent déjà à votre attente. Cette pertinence reste une responsabilité du modèle. Le plugin exige une mise à jour des connaissances avant l’écriture, vérifie que le texte n’a pas changé pendant la tâche et archive les versions. Sans correction ni demande, la révision est refusée. Les protections plus étroites des envois ordinaires restent distinctes du bouton Réviser.

Après une révision ciblée, les mots ajoutés ou remplacés par Codex apparaissent sur fond jaune dans l’éditeur, en mode source comme en aperçu en direct. Un petit repère jaune indique une suppression ; son infobulle contient le texte retiré. Ces décorations CodeMirror ne modifient pas le Markdown : aucune balise de surlignage n’est ajoutée. Les références sont conservées dans les données du plugin pour retrouver le surlignage après réouverture. Les repères suivent les déplacements de texte ; une intervention humaine dans une zone surlignée retire son repère. Les relevés de correction distinguent les passages modifiés, sans englober les paragraphes intacts qui les séparent.

Le bouton **Accepter** apparaît pour le chapitre ouvert lorsqu’une révision reste à accepter. Il retire son surlignage et conserve la version actuelle comme exemple positif dans un relevé horodaté de `Bible/Suivi/`, référencé dans `Bible/suivi.md` et `Bible/Suivi/Connaissances.md`. Le texte saisi dans le chat accompagne l’acceptation et reste conservé mot pour mot, même pour un retour bref comme « Enfin, voilà ce que je voulais ». Codex consulte ces exemples et ces retours lors des prochaines demandes. L’acceptation conserve le manuscrit et ses archives ; les références de diff restent disponibles pour les futures corrections. Si l’enregistrement échoue, le surlignage et le message restent disponibles. Accepter ne lance aucune requête au modèle.

Les chapitres comportant des corrections humaines sont également protégés lors d’un envoi ordinaire dans le chat : les zones sont figées avant le lancement de la tâche. Les consignes ajoutées pendant son exécution ne les élargissent pas. L’écriture d’un chapitre sans correction humaine connue et la création d’un nouveau texte restent disponibles dans les demandes ordinaires.

Pendant une tâche Codex, la note active du projet et les notes dont Codex demande l’écriture passent temporairement en lecture seule dans tous leurs éditeurs ouverts. La saisie, le collage et les commandes d’annulation sont bloqués ; la sélection, la copie et les mises à jour du fichier restent possibles. Les autres notes restent éditables. Le verrou est levé à la fin de la tâche, après son arrêt ou une déconnexion ; désactiver le plugin retire aussi ce verrou. Un état de lecture seule déjà imposé par Obsidian ou une autre extension est conservé.

Codex demande les créations et modifications à l’outil MCP local Orelius `ecrire_fichier(chemin, contenu)`. Le plugin contrôle le chemin, archive le contenu original et une copie exacte du nouveau texte, puis publie lui-même le fichier de manière atomique. La version générée est conservée dès la première création pour permettre un diff avec les corrections humaines ultérieures. L’arborescence est reproduite et chaque copie reçoit une date et un identifiant distincts : avec les noms par défaut, `Manuscript/Chapitres/texte.md` devient par exemple `Archives/Manuscript/Chapitres/texte.<date>-<identifiant>.md`. Les fichiers de la bible sont conservés sous `Archives/Bible/`. Les versions précédentes sont conservées. Si l’archivage échoue ou si la note contient des modifications non enregistrées dans l’éditeur, l’écriture est refusée. Une création n’a pas d’original à archiver, mais son texte généré est archivé avant publication. Le plugin confirme le résultat à Codex après l’écriture et l’enregistrement de la référence de suivi.

Les commandes de Codex restent dans un bac à sable en lecture seule. Les écritures directes, patches et extensions de permissions sont refusés automatiquement ; seules les écritures du plugin passent. Le serveur MCP Orelius est intégré au processus Obsidian, écoute uniquement sur `127.0.0.1` avec un jeton éphémère et reste lié à la tâche active. Le jeton est transmis à Codex par une variable d’environnement ; il n’est pas enregistré dans la configuration ou l’historique. Les autres serveurs MCP, apps, plugins Codex et la délégation sont désactivés dans le processus lancé par Orelius. La configuration globale de Codex n’est pas modifiée. L’outil est également disponible à la reprise des conversations existantes. Les suppressions, déplacements, liens symboliques et modifications du dossier d’archives configuré, de `_Archives`, du dossier de configuration réel d’Obsidian ou de `.git` ne sont pas pris en charge. Les lectures utilisent les permissions de Codex : choisir un dossier de travail ne constitue pas une restriction de lecture à ce dossier. Une réponse textuelle dans le chat ne crée pas de texte littéraire sans demande ; les attentes éditoriales nouvelles peuvent enrichir la base de connaissances du suivi.

Messages et questions partagent une zone de défilement ; les commandes et le champ de saisie restent visibles. Le panneau suit les nouvelles réponses tant que vous restez en bas de la conversation ; remonter permet de relire l’historique. Le contenu précédent reste affiché pendant la préparation du nouveau rendu Markdown et le suivi tient compte des changements de taille, notamment au chargement des images. Une question en attente devient visible avec son champ de réponse, ses choix éventuels et le bouton **Répondre**. La touche **Entrée** valide le formulaire de réponse.

Le chat affiche les demandes de l’auteur et les réponses finales. Les prompts techniques ajoutés par Orelius, les outils et les commentaires intermédiaires restent hors du fil ; l’indicateur de travail, les erreurs et les questions de Codex restent visibles. Réviser applique les remarques du chat et les annotations à tout le chapitre : correction des occurrences concernées et des raccords, conservation du reste. Les attentes générales alimentent les Consignes actives pour la suite.

Sous chaque réponse finale de Codex, les boutons cœur, pouce levé et pouce baissé permettent de noter l’échange. Le texte éventuellement saisi dans le chat accompagne la réaction, mot pour mot. Une note reste sélectionnée après réouverture ; la changer remplace l’avis courant dans la base de connaissances et conserve les avis précédents dans les relevés horodatés de `Bible/Suivi/`. Chaque relevé conserve les demandes, la réponse évaluée et les précisions de l’auteur. Codex peut en tirer des consignes et des exemples de ce qu’il faut reproduire ou éviter lors des prochains échanges, sans réentraîner le modèle. Noter ne lance aucune requête au modèle et ne retire pas le surlignage du manuscrit.

Une gomme **Effacer le surlignage** apparaît après ces trois réactions lorsque le chapitre ouvert contient des marques de révision. Elle retire les marques de ce chapitre, y compris après réouverture, sans accepter les modifications ni enregistrer d’avis. Le texte, les références de diff et le message en préparation dans le chat sont conservés.

Les réglages et l’identifiant de la conversation de chaque dossier sont enregistrés dans les données du plugin. Revenir dans un dossier retrouve sa conversation, y compris après un redémarrage d’Obsidian. L’historique reste géré par Codex et est rechargé à la reprise. **Nouvelle conversation** remplace uniquement l’association du dossier actif ; les anciens historiques restent dans Codex. Une conversation enregistrée avec l’ancien format est conservée pour son dossier. Les messages et les documents que Codex consulte peuvent être transmis au fournisseur configuré dans Codex. Orelius ne conserve aucune clé d’API.

## Contexte de rédaction visible

Chaque manuscrit possède un dossier `Context/`, sous le nom de dossier défini dans les réglages. Pour le chapitre `Manuscript/Chapitres/002.md`, Orelius conserve `Manuscript/Context/002/sources.md` (demande, sources retenues et empreintes) et `preparation.md` (situation, objectif, actions, connaissances du narrateur et du lecteur, arrivée, corrections et incertitudes). Ces documents sont produits par le plugin ; leur remplacement archive l’ancienne version dans le dossier d’archives configuré. Le fichier `prompts.md` conserve les consignes exactes transmises par les outils pour cette tâche ; `retours-auteur.md`, lorsqu’il existe, est inclus parmi les retours. Aucun bouton de validation supplémentaire n’est nécessaire.

Le dossier est reconstruit lors de la consultation éditoriale, à chaque demande. Il distingue le manuscrit actuel, le chapitre précédent choisi par la configuration, ou par ordre naturel des noms dans le même dossier, les intentions du plan, les fiches de référence et un extrait de voix accepté. Vérifiez ce raccord si votre ordre narratif ne suit pas les noms de fichiers. Les références sont sélectionnées suivant leurs noms, alias, modes et conditions dans la [configuration](Contexte.md) ; les autres fiches restent listées et consultables. Les anciens résumés, notes de personnages par chapitre et conversations ne sont pas injectés comme faits établis. Seule la rubrique Consignes actives de la mémoire est injectée ; le reste reste disponible à la demande.

Les méthodes sont définies dans les fichiers `prompts/preparer-scene.md`, `rediger.md`, `reviser.md`, `controler-continuite.md` et `actualiser-suivi.md`, intégrés au plugin à la compilation. Le dossier reçoit d’abord le prompt de préparation ; après préparation, l’outil transmet et conserve celui de rédaction ou de révision, le contrôle et le suivi. Ces étapes ne nécessitent pas cinq appels distincts au modèle. L’ancien dossier `context/<Manuscript>/Chapitres` est déplacé vers `<Manuscript>/Context` à la préparation du projet ; si les deux emplacements existent, le plugin s’arrête sans écraser aucun fichier.

Codex enregistre la préparation avant de rédiger. Une source modifiée impose de reconstruire le dossier ; une consigne envoyée pendant la tâche invalide aussi sa préparation. Les contrôles de portée, d’archivage et de modification concurrente restent appliqués lors de l’écriture du manuscrit. Le plugin vérifie la présence et la fraîcheur de la préparation, pas la qualité littéraire ni la justesse de toutes les interprétations.

## Agent du projet

Le journal `Bible/Suivi/Conversation.md` conserve les prompts de l’utilisateur et les réponses finales de Codex, sous des titres de date comme `# Lundi 26 octobre 2026`. Les commentaires intermédiaires, raisonnements, commandes et événements techniques sont exclus. Il est actualisé après chaque tâche terminée et à la reprise d’une session, à partir de l’historique Codex. Les anciennes sessions du même projet sont conservées ; reprendre la même session ne crée aucun doublon. Les dates manquantes dans un ancien historique sont indiquées comme inconnues. Pour les anciens messages sans phase, seul le dernier message assistant d’un échange terminé est retenu. Le nom de la bible suit les réglages. Le plugin gère les sections de session du journal ; les notes personnelles placées ailleurs sont conservées et chaque modification archive d’abord l’original.

`Bible/Style/Narration.md` définit le mode narratif et le style narratif des textes romanesques. Si ce fichier manque et que l’ancien `Bible/Narration.md` existe, son contenu est copié vers le nouvel emplacement en conservant l’ancien fichier. Sinon, le plugin crée un canevas à compléter. Une narration déjà présente dans `Style` est conservée. `Bible/Personnages/` accueille les fiches générales des personnages : identité, caractère, parcours et relations. Codex consulte la narration et les fiches pertinentes avant d’écrire ou de réviser, pour respecter le point de vue, les temps du récit et la continuité des personnages. Ces chemins suivent le nom de bible configuré ; les documents existants sont conservés.

Le dossier `Bible/Style/` accueille les consignes d’écriture de l’auteur et, éventuellement, des textes exemples. Codex les consulte avant d’écrire ou de réviser, en distinguant les consignes explicites des préférences déduites des exemples. Le nom de la bible suit les réglages ; le dossier `Style` et son miroir dans les archives sont créés automatiquement, sans modifier les documents existants.

Le suivi des corrections est vérifié au retour dans le chat et juste avant chaque envoi, sans surveillance en temps réel. Le plugin garde comme référence le dernier texte de chaque chapitre effectivement écrit par Codex, y compris après redémarrage. Les coupes, réécritures, passages barrés `~~...~~` et commentaires `(((destinés à Codex)))` sont consignés dans des relevés horodatés sous `Bible/Suivi/`, indexés par `Bible/suivi.md`. Le nom de Bible suit le réglage du projet. Un texte inchangé ne produit aucun relevé supplémentaire. Les consignes personnelles de l’index sont conservées.

Codex construit aussi `Bible/Suivi/Connaissances.md`, une base éditoriale propre au projet, consultée à chaque demande et conservée entre les sessions. Il la crée dès qu’un enseignement utile apparaît dans un échange éditorial ou des corrections, puis la complète avant sa réponse finale. La synthèse distingue les consignes explicites, les hypothèses tirées des exemples et les contradictions ou évolutions. Chaque attente précise sa portée, sa date et ses sources ; une coupe isolée ne devient pas une règle générale. Les demandes actuelles de l’auteur priment, les attentes remplacées sont signalées et les notes personnelles sont conservées. Sans enseignement nouveau, le fichier reste inchangé. Ce fichier peut être écrit par Codex via l’outil du plugin, avec archivage de l’original et du résultat ; les relevés horodatés, leur index et le journal restent protégés. Aucun apprentissage n’est lancé en temps réel ou en arrière-plan : la synthèse est réalisée par Codex pendant les demandes, sans modification des paramètres du modèle.

La création d’un relevé ne modifie pas le chapitre. Avant une réécriture demandée par Codex, le texte actuel est archivé ; s’il diffère de la référence Codex, le nom de cette version humaine se termine par `-h.md`. Le nouveau texte produit par Codex possède ensuite sa propre copie archivée, sans suffixe `-h`, préparée avant publication. Les références utilisées par le suivi sont aussi enregistrées dans les données locales du plugin. Un chapitre écrit avant l’installation de ce suivi n’a pas de référence fiable : la comparaison devient disponible après sa prochaine écriture par Codex. Les relevés conservent les différences observées ; ils ne fabriquent aucune conclusion stylistique. Le modèle d’agent demande à Codex de les consulter avant une reprise ou un nouveau passage.

Le générateur intégré au plugin [generate-agent.ts](../plugin/src/generate-agent.ts) crée `AGENTS.md` à la racine de chaque projet d’écriture lors de sa préparation. Le modèle [prompts/agent.md](../prompts/agent.md) décrit les dossiers et le rôle de l’assistant d’écriture. Ses variables `{folder}`, `{manuscriptFolder}`, `{modelFolder}`, `{bibleFolder}` et `{archiveFolder}` reçoivent les valeurs des réglages du plugin ; toute variable inconnue est signalée.

Le générateur gère uniquement la section comprise entre `<!-- orelius:agent:start -->` et `<!-- orelius:agent:end -->`. Les consignes personnelles situées ailleurs sont conservées. Si le fichier existe sans ces marqueurs, la section est ajoutée à la suite. Chaque modification d’un `AGENTS.md` existant conserve d’abord son original dans le sous-dossier `Agents` du dossier d’archives configuré, soit `Archives/Agents/` par défaut. Une génération identique ne modifie rien. Des marqueurs incomplets, un lien ou un échec d’archivage bloquent la mise à jour.

Le même modèle alimente le contexte envoyé à Codex lors de l’ouverture ou de la reprise d’une session, pour que les dossiers et le rôle restent cohérents avec les réglages actuels. Après modification du modèle, recompilez puis rechargez le plugin.
